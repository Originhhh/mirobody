# Code-tool language probe: JS `eval` vs Python

`eval_language_probe.py` asks the same eight synthetic aggregation questions of
the same local model, with the same readings, and changes only the tool that
does the arithmetic: JavaScript `eval` (QuickJS, the runtime Mirobody ships) or
`python_exec`.

This is a probe, not a leaderboard. It exists because a local MiniCPM5-2B was
observed writing Python into Mirobody's QuickJS `eval` tool. The probe measures
that mismatch under controlled conditions.

## Method

- Model: `MiniCPM5-2B-Q8_0` through llama.cpp `llama-server` (build 11269),
  temperature 0, thinking on, 32k context.
- Data: one synthetic person, readings generated by the probe (resting heart
  rate, sleep, weight, blood pressure, HbA1c, steps, LDL, fasting glucose).
- Questions: eight aggregation tasks (monthly means, a change, a percentage,
  a total, a unit conversion). Ground truth is computed from the same rows,
  never typed by hand.
- Prompt: neutral about language. It says to use the available code tool, and
  the tool description says `data` holds the rows from the last query.
- Scoring: every expected number must appear in the final answer within a
  tolerance. A case passes only when all of its numbers are present.
- Two runs per arm, 16 cases per arm.

## What the calls show

The JS arm's failures were not random syntax noise. The model repeatedly wrote
Python into the JavaScript tool:

- `#` comments, `import statistics`, `print(f"...")`, `sum(...)`,
  `for x in data:`, and bare assignment to `data`.
- `bp_q2` used all five code calls on Python-in-JS attempts
  (`SyntaxError: Unexpected identifier 'statistics'`, then `expecting ';'`),
  never reached an answer, and ended with empty content.
- `steps_august` did the same with `sum is not defined`, `Unexpected identifier
  'x'`, and `print is not defined`, also ending empty.
- `weight_change` and `glucose_convert` passed only because the model gave up
  on the tool and did the arithmetic in its head; `glucose_convert` first used
  `1 mg/dL = 1/180` (0.558 mmol/L), and the Python arm answered 5.58.
- Even the JavaScript it did write had bugs: `sleep_july` first returned `NaN`
  and concatenated the numbers as a string.

The Python arm had no code errors in either run. The model's code was ordinary
Python: `statistics.mean`, `sum`, `len`, f-strings, `json`.

The pass rates understate the difference: in the JS arm two cases produced no
answer at all, and two more passed only by mental arithmetic. The code-error
rate and the clean-pass count are the sharper signal: 28 of 36 JS calls failed,
against 0 of 14 Python calls.

## What changed in the product

The local `MODELS` entry now sets `code_tool: python`: the chat agent gets
`python_exec` (`mirobody/agent/python_tool.py`) and no QuickJS `eval` or PTC.
The tool runs code in the local sandbox (`mirobody/agent/python_sandbox.py`);
`PYTHON_SANDBOX_IMAGE` switches it to Docker with no network and a read-only
root. `code_tool: eval` keeps the previous REPL for cloud models.

## Caveats

- Eight questions, two runs, one 2B model. Directional, not significant.
- The probe preloads `data` and does not implement PTC. Mirobody's real `eval`
  exposes `tools.queryHealthIndicators`; that is a different surface, and the
  shipped prompt also mentions `eval` by name. Both would bias the JS arm
  further, not less.
- `python_exec` here is a local subprocess, not the hardened runner container
  proposed for production. The probe measures the model's code language, not
  the sandbox boundary.
- The `rhr_monthly` tolerance is 0.06 because its monthly means are close
  together; a looser tolerance let a wrong March mean pass on a June value.
- An earlier Node-based JS arm (same questions, same model) scored 14/16 with
  a 56% code-error rate. QuickJS is stricter and is the product runtime, so
  the table above uses QuickJS.

## Reproduce

```bash
# from the repository root, with the Q8_0 GGUF already downloaded
/Users/admin/Desktop/development/Mirobody/local-models/llama-stock/llama-b11269/llama-server \
  -m /Users/admin/Desktop/development/Mirobody/local-models/small/minicpm5-2b/MiniCPM5-2B-Q8_0.gguf \
  --chat-template-file docker/minicpm5-2b.jinja \
  --host 127.0.0.1 --port 8088 -c 32768 -ngl 99 --jinja --reasoning on

./.venv/bin/python benchmarks/local_agent/eval_language_probe.py \
  --base http://127.0.0.1:8088/v1 --model minicpm5-2b \
  --tool js --out /tmp/eval-js.json

./.venv/bin/python benchmarks/local_agent/eval_language_probe.py \
  --base http://127.0.0.1:8088/v1 --model minicpm5-2b \
  --tool python --out /tmp/eval-python.json
```
