Mirobody 架构详解

Mirror your body in data —— 把化验单、可穿戴设备、基因文件等异构来源，统一成一套标准（LOINC / UCUM / ICPC-3）， 存在你自己的机器上，并让 AI agent 通过 Web 聊天或 MCP 来查询。本页基于仓库源码与 docs/ 整理。

1. 分层规则：为什么这样切

三层不是约定俗成，而是被 lint-imports（pyproject.toml 里 6 条 import-linter 契约）机器检查的，违反即构建失败。

层目录安装方式允许依赖
② 标准化 + 内核（库）engine/ lexical.py units/ value_scale.py zh_fold.py _bundle.py _strtab.py
standardize/ 的纯函数部分
kernel/、testing/		pip install mirobody（仅 numpy，约 2 个包 / 67 MB）只能互相依赖
② 中触达数据库的部分standardize/aggregate/ derive/ indicators_info.py canonical_units.py value_range_validator.py[app]不得依赖 agent 框架
① 采集 + 存储 + MCPdocuments/ collect/ utils/ user/ task/ mcp/[parse] / [app]不得 import langchain* / langgraph / deepagents
③ Agentagent/ server/[agent] / [app]任意
核心思路：“健康数据是什么意思”（单位、日边界、聚合策略、选举规则）全部写成纯函数放在最底层；数据库、LLM、agent 框架都只是它的消费者。 于是同一套语义既能被 uvx mirobody resolve 离线调用，也能被完整 App 使用，且两边不会算出不同的答案。

其他硬约束：collect 和 standardize 各只有一个“前门”；新增库层模块必须放进 kernel/ 并登记到全部 4 条相关契约里；scripts/check_wheel_data.py 保证构建期的 bundle 生成代码不进 wheel。

2. ② 标准化 + 内核层（展开）

这是项目的心脏，也是唯一会发布到 PyPI 被别人当库用的部分。分三块：engine/units（词汇：名字与单位）、kernel（语义：数据意味着什么）、standardize（把一个值编码成一行的“接缝”）。

2.1 engine/ 与 units/ —— 名字和单位

模块做什么
engine/resolver.py词法级指标名解析：对照随包发布的 LOINC bundle（res/），约 92 万别名，CJK 感知分词
engine/parse.py文档 → 读数：一次 LLM 调用抽取，然后交给离线 resolver 编码
engine/observation.py读数表达为 FHIR Observation（standardize_reading 的输出形状）
lexical.py / zh_fold.py表面折叠（全半角、繁简等）+ 分词
模块做什么
units/normalize.py自由文本单位 → 规范 UCUM（如 mmol/L、10^9/L）
units/convert.pyUCUM 换算，让一个指标在一个单位下成为一条序列（含 mg/dL ↔ mmol/L 这类需分子量的）
units/families.py单位 → LOINC PROPERTY 族（质量浓度、物质浓度…），防止跨族误合并
units/essence.py原样附带 UCUM 规范自己的单位表并做自检

# 血红蛋白、ヘモグロビン → 718-7（同一个 LOINC）
# 血脂 → 不解析：它是一类检查，不是一项检查（宁可不答，不错答）

2.2 kernel/ —— 健康数据的“语义”，全是纯函数

模块职责它防止的失败
metrics.py设备指标目录：名字 → (system, code)、state_class、aggregation_policy、日窗口 window、目录单位 unit_ucumLOINC 有争议时不硬给码，用 mirobody-device 命名空间，避免把两种检查悄悄画进一张图

quality.pytime_gate（无开始、结束早于开始、跨度 >36h、未来时间）、value_gate（百分比越界、非有限数）等只拒绝物理上不可能的；拒绝都带原因码，不是自由文本异常
series.py一天的读数是什么、如何汇总（5 种策略）、elect 来源选举、coverage_bound步数不会被“取平均”；重叠时间段并集而不是相加
overlay.py修正是覆盖层 Override，原行永不改写以前每次修正都是 UPDATE，源头重推一次就被悄悄覆盖回去
meds.py用药：计划、排期出的剂量、实际服用；slot_state 由时钟实时算 due/missed/upcoming存下来的 “missed” 在用户补标“已服”那一刻就成了谎言 → 派生值不入库
query.py唯一读取权威；view 是分派表 DISPATCH；ROW_CAP=50、BUCKET_CAP=92以前聊天和仪表盘各读一份，同一个周二会给出两个数
tools.py工具返回什么（Envelope）、如何失败、何时允许重调治理读信封，不读模型的散文 → 阻止死循环重试
evidence.py统计产出证据，模型只负责叙述模型不自己“算”结论
citations.py回答的引用格式，校验每个数字都能追溯到被引的行回答里出现无出处的数字
connect.py凭证状态机 linked→refreshing→expired→revoked、退避、PullWindow、backfill_windows用户改了厂商密码后无限重试，被厂商当攻击锁号
sink.py / events.py / memory.py / ops.py写入契约 / 与传输无关的 AgentEvent 流 / agent 只读的长期记忆文档 / 不含健康数据的可观测性日志泄露 PHI

2.3 standardize/ —— 一个值如何变成一行

standardize 是“纯接缝”：把印出来的名字、单位、值，变成一个 Coding 和写入时就确定的列。它的纯函数部分属于库层，aggregate/、derive/ 等触达数据库的部分属于 [app]。

模块输入 → 输出
fold.py印刷名 → 身份键（全项目只有这一个折叠）
parse.py值的类型层：数值 / 定性（“阴性”）/ 区间… → value_kind、value_num；“阴性”永远不会被平均
local_day.py一个瞬间属于哪个本地日（含睡眠 18:00 锚点、DST）—— 唯一实现
series.pyseries key：什么可以画在同一根轴上（跨单位、跨人）
code.pycode()：名字 + 单位 + 值类型 → 一个 Coding，或一个原因（outcome.py）
names.py编码后的读数在读者语言里叫什么、测的是什么
devices.py设备对照表：可穿戴字段对应哪个 LOINC，哪些字段 LOINC 根本没有码
icpc3.pyICPC-3：用户说哪里不舒服、被告知有什么病（症状/诊断日志）
genotype.py / pgx.py基因型按公开站点记录归一化；离线 CPIC 药物-基因证据（明确推断边界）
terminology.py3 个术语工具的函数体，MCP、stdio、agent 共用

3. ① 采集层（展开）

负责“把外部世界的数据拿进来”，不理解数据的含义 —— 含义全部委托给 ② 层。

3.1 文件链路：化验单、基因文件

  1. 上传：POST /files/upload（server/routers/file_router.py）→ collect/files/file_upload_manager.py，记录上传状态 upload_state.py
  2. 按类型分派：handlers/factory.py 选 pdf / image / excel / document / text / genetic handler
  3. 文件 → 文本：mirobody/documents/ —— detect 识别类型，extract 取 PDF 文本层，只有扫描页才走 ocr，render 渲染页面
  4. 抽取指标：services/indicator_extractor.py / table_indicators.py 用 LLM 抽出“名字、值、单位、参考范围、日期”（report_date.py 定报告日期）
  5. 编码：交给 ② 层 engine.resolve + standardize.code()
  6. 写入：indicator_store.py → collect/observations.py（唯一写入口）
  7. 基因文件另走 genetic_processor.py → genotype_format.py → genetic_store.py，用 standardize/genotype.py 对照 dbSNP 站点归一化

3.2 设备链路：可穿戴 & Apple Health

  1. 连接：collect/providers/_platform/base.py 的参考拉取循环，每次先问 connect.may_attempt，失败调用 record_failure 退避
  2. 拉取：按 PullWindow 分块（长历史由 backfill_windows 切成有界窗口），原始 payload 存在各 provider 自己的表里
  3. 解码：kernel/decoders/<vendor>.py → Fact；目录不认识的 key 返回空并隔离，绝不猜相近的名字
  4. 入库：collect/ingest/services → observations.py
  5. Apple：apple_router 的 /apple/health、/apple/cda，以及 export.zip 导入；三种传输（App、export、Watch）保持为独立流，选举时再挑出一个 Apple 代表

已内置 provider：mirobody_garmin_connect、mirobody_oura、mirobody_whoop、apple。接入新设备的契约： format_data(self, fmt_input: FormatDataInput) -> StandardPulseData 和 _validate_credentials(self, credentials: dict)，详见 docs/provider-guide.md。

刻意不做的：调度平台、webhook、多账户扇出、分布式锁、OAuth 令牌存储 —— 这是一个库加一个参考应用，不是同步平台。

4. 存储层（展开）

4.1 关键表与“写入时就确定”的列

DDL 在 mirobody/schema/：10_accounts · 20_files · 30_observations · 31_medications · 32_genomics · 40_devices · 41_device_rules · 50_chat · 60_tasks · 62_personal_mcp · 63_settings · 90_retire，开发环境启动时回放。

列（th_observation / th_coding_current）来源为什么在写入时算
local_datestandardize.local_day + 指标 window + 行自己的 tz“这是哪一天”是读数的事实；读时再算，每个读者都会算得不一样

series_idLOINC 轴，或 local:<name>|<unit>决定什么能画在一根轴上
stream_keyname|unit|source:vendor两台设备的曲线绝不被平均到一起
source_class来源选举的第一判据
fingerprint原文字段 + 时间没变化的重新同步什么都不写

表是只追加的：更正/撤回是一条指向旧行的新行（amends），读视图隐藏旧行；唯一的 DELETE 是隐私删除路径。用户修正写入 th_override。

4.2 聚合、选举、派生（worker）

state_class聚合策略原因
instantmean_min_max / last心率是采样
cumulativesum_delta步数是增量
interval / sessionduration_union重叠时段不能算两次
provider_dailyprovider_value厂商已算好当天值，直接投影

选举（series.elect → aggregate/election.py → th_day_authority）：两台设备都测了同一天，各自都对。排序依据：

  1. 真实测量者 > 个人资料回显
  2. 覆盖度
  3. 测量时刻（不是行更新时间）
  4. 部署方自己的优先级

数值不可能（睡眠比夜晚还长）的候选直接拒绝；全部失败则保留已发布值，原因写进 th_check_result。从不混合两个来源求平均。

派生：standardize/derive/rules.py 计算没有设备直接测的量（睡眠效率、心率区间）。

5.1.1 一次回合从头到尾

分两段。外层 agent/chat/turn.py::run 管权限、存档和 SSE；内层 MirobodyAgent.generate_response（agent/agent.py）管模型和工具。外层只认 registry.AbstractAgent 这个契约，所以内层可以整个换掉。

外层：chat/turn.py
  1. _access：判定这一轮读谁的记录（自己，或照护圈里的另一个人），得到 may_read / may_write。没有写权限时不能带附件。
  2. _store_files 登记附件；_save_question 先把用户这条消息写库，回答行的 question_id 才指向存在的行。
  3. _agent_kwargs 组装 language、session_id、file_list、provider、timezone、record_owner、may_write，调用 agent。
  4. _pump 转发 agent 产出的 blocks；文本块经 _attach_citations：只有数字、单位、指标名都能无歧义对上某一行时才挂引用，对不上的保持无引用。
  5. _save_answer 存完整记录后才发 end，因为前端看到 end 就会重新加载历史。
  6. _summarize_once 后台给新会话生成标题摘要。
内层：generate_response
  1. _chat_model(provider) 从 MODELS 里挑模型；请求的模型不可用时换默认模型并发一个 notice 块。本地模型还在加载就直接回一句提示。
  2. _load_tools：通过 tool_loader.py 把 MCP 注册表里的工具转成 LangChain 工具，把 user_info 用 functools.partial 绑进去，并从 schema 里删掉这个参数，模型看不到也改不了。
  3. _build_system_prompt 用 Jinja 严格渲染：模板引用了 harness 没提供的变量就直接报错。
  4. 探测模型能力：能否收文件块、能否看图、上下文窗口多大（_fit_window）。
  5. _build_agent：建虚拟文件系统、中间件栈、检查点，调用 harness.assemble。
  6. pending_answer：线程正停在 ask_user 上，这条消息就作为回答恢复；否则附加本轮说明（时间、回答语言、附件）。
  7. agent.astream(stream_mode=["messages","updates","custom"]) → TurnStream 转成 blocks；最后发一个 usage 块。
错误只向用户报异常的类型名（client_safe_error）。原因是厂商的错误体会回显提示词，数据库驱动的错误会回显 SQL 和参数，以前它们通过 str(e) 漏到了浏览器和聊天记录里。

5.1.2 harness.py：组装 deepagents

harness.assemble 是所有基于 deepagents 的 agent 共用的组装步骤。它刻意关掉了 deepagents 的几项默认能力：

  • 没有子 agent：要同时做两件事才能真正关掉 task 工具：按模型实例解析出的 provider key 注册一个禁用通用子 agent 的 profile，并传 subagents=[]。这个 key 不是配置里的 llm_type，而是 deepagents 从模型类推导的（如 ChatAnthropicVertex → anthropicvertex）。注册错 key 不会报错，生产环境出过一次模型调用了 task 的事故。
  • 没有写类原生工具：_EXCLUDED_NATIVE_TOOLS = {delete, write_file, edit_file, execute}。模型不能写文件，也不能执行 shell。
  • 没有 todo 列表：deepagents 0.7 起默认不带 TodoListMiddleware，这里也没加回来，所以没有 write_todos。

5.1.3 中间件栈（由外到内）

#中间件解决的问题
1ToolFaultMiddlewareLangGraph 的 ToolNode 默认把工具异常往上抛，整轮对话断掉，驱动错误原文还可能到达用户。这里改成一条错误 ToolMessage，模型可以换条路。
2RetryGovernanceMiddleware工具已经返回不可恢复的错误（比如无权读取），模型换个说法再调，会把预算耗光。调用前查 kernel.tools.RetryLedger：同一个（工具, 规范化参数）已经不可恢复地失败过，就直接拒绝。上限 _RETRY_LIMIT = 2。
3InvalidToolCallRepairMiddleware参数 JSON 解析不了的调用到不了任何工具，原本会让回合空着结束。这里把解析错误回给模型重试。
4EmptyAnswerRepairMiddleware推理模型把整个回答写在推理通道里，正文为空也没有工具调用。实测 Bonsai-27B 四次出现一次。这里点名再要一次答案，第二次还空就按空回合结束。
5ModelCallBudgetMiddleware每轮最多 MODEL_CALL_LIMIT 次模型调用（默认 50）。最后一次调用关掉工具并要求作答，所以死循环也会以一个回答结束，而不是 "Model call limits exceeded"。
6ToolCallLimitMiddleware（每个工具一个）query_health_indicators 12 次、code_exec 8 次、search_medical_knowledge 3 次、read_medical_source 2 次。超限只移除这个工具，回合继续。
7NoVisionReadMiddleware（仅不能看图的模型）deepagents 的 read_file 按扩展名把 .png 包成图片块，纯文本模型会报 500。这里换回 OCR 文本。
8GenotypeSafeSummarizationMiddleware + GenotypeRowGuardMiddleware基因型数据行不进对话摘要和历史文件；检查点里上一轮的基因型结果不会在下一轮被重放给模型。
9UniversalPromptCachingMiddleware（最后一个，它的决定生效）上游只给 Anthropic、Bedrock、Fireworks 接了提示缓存；这里覆盖 Claude、Gemini、OpenAI、DeepSeek（含经 OpenRouter），TTL 5 分钟。

每轮都新建一套中间件，所以重试账本也是每轮一份，“已经试过”只在本轮内有效。

5.1.6 记忆与 ask_user

检查点（checkpointer.py）：LangGraph 的 Postgres 检查点按 thread_for（提问者 + 会话）保存真实的消息对象，每轮只传入新消息。它替代了一套 424 行的手写回放：以前每轮把 SSE 记录解析回 LangChain 消息，推理内容丢失，工具参数变成重新解析的字符串。数据库不可用时降级为无状态回合，不报错。

ask_user（hitl.py）：典型场景是“这份附件的检查日期是哪天”。模型调用后，工具体不执行，HumanInTheLoopMiddleware 在模型步之后暂停图，前端收到一个 interrupt 块（问题 + 选项），回合结束。用户的下一条消息通过 Command(resume=...) 恢复同一个线程。它不属于 MCP，因为 MCP 客户端没有回答它的界面。

5.1.8 模型、替换与扩展

  • 模型：models/clients.py::build_chat_model 按 llm_type 构造客户端（OpenAI 兼容端点、OpenRouter、Gemini、Anthropic、本地服务等）。缺 key 的条目放一个占位客户端，零 key 部署也能启动，/api/models 只列出可用的。mirobody doctor --probe 会发真实请求，检查模型能否调用工具、读图、遵守 schema。
  • 替换 agent：registry.py 先找 mirobody.agents entry point，再按顺序找 AGENT_DIRS，第一个定义了 generate_response 的类成为本进程的 agent。契约只有 __init__(**kwargs)、可选的 load_llm_clients、异步生成器 generate_response(user_id, messages, **kwargs)。messages 只含本轮，对话状态由 agent 自己管。最小示例：examples/mirobody_example_plugin/。
  • 加工具：mirobody.tools entry point 或 MCP_TOOL_DIRS。工具同时出现在聊天和 MCP 里。
  • 评测用时钟：clock.py 允许评测请求固定“今天”（EVAL_AS_OF_ENABLED，默认关），回放旧数据时“最近 30 天”才有意义。

5.2 工具、信封与 HealthQuery

原则：一类数据一个工具，每个参数对每次调用都适用。“总是连着调用的合并”（搜索 + 读取合成一个），“语法不同的拆开”（用药单独一个工具）。

query_health_indicators(keywords | indicators, start, end, view)
query_medications      (view=plan|log|history, keywords, start, end)
query_genetic_data     (rsids | gene | chromosome+start+end+build)
query_pharmacogenomics (drugs | genes)
  • 没有参数能指定“某个人”：调用只读当前认证身份的记录（MCP token/URL，或聊天打开的那份记录，聊天层预先授权）。
  • schema 扁平且封闭（additionalProperties: false）：未知参数返回结构化、可恢复的拒绝，例如 error (invalid_arguments): kind: unknown parameter。
  • view 是分派表：raw（每指标最多 50 行）、minute/hour（最近 92 个桶）、day 及更粗（取选举结果）、stats（含 first / first_date）…；不带选择器时返回指标目录。
  • 返回 tools.Envelope：状态、出处、截断信息与渲染文本并列；中间件只看信封，不看模型的散文。
  • 症状/诊断（ICPC-3）和读数同表同序列：keywords=["headache"] 能找到写成“头疼”的条目。

7. 两条完整链路

A. 上传一份化验单

  1. 前端 Data 页上传 → file_router
  2. handler 选择 → documents 取文本（扫描页才 OCR）
  3. LLM 一次抽取：名字 / 值 / 单位 / 日期
  4. engine.resolve：“低密度脂蛋白胆固醇” → LOINC
  5. units.normalize + convert：mg/dL ↔ mmol/L
  6. standardize.code() → Coding + series_id
  7. observations.prepare：时间门、值门 → 计算 local_date、fingerprint → INSERT
  8. worker 聚合 / 选举 / 派生

B. 问 “我的胆固醇怎么变了？”

  1. 前端 chat → SSE 会话（agent/chat），照护圈授权
  2. MirobodyAgent 加载提示词与模型
  3. 模型调用 query_health_indicators(keywords=["cholesterol"]) → 返回目录匹配
  4. 再调用 indicators=[...] view="day" → HealthQuery 读选举结果
  5. 返回 Envelope（状态、出处、截断、窗口语义）
  6. 可选 code_exec 计算趋势；citations 校验每个数字可溯源
  7. wire 把事件转成 blocks，流式推回前端；带下划线的数字可点开原始读数与文件

9. 十条不变量（每条都有测试）

  1. 读数属于哪一天，由目录窗口在写入时一次决定。
  2. 指标单位来自目录；解码器换算到它，从不声明它。
  3. 未映射的指标被隔离，绝不猜测。
  4. 选举只在发布前发生一次，一天只有一个权威来源。
  5. 重叠时段取并集，绝不相加。
  6. 厂商自己的日值直接投影，绝不再平均，也不与其明细相加。
  7. 时间绝不捏造：没有时间的记录解码为空。
  8. 修正是覆盖层；已存的行不被改写。
  9. 每个回答都说明产生它的窗口语义。
  10. 日志只含 id、计数、时长、状态码、类型名 —— 永不含值（指标名也不行）。
